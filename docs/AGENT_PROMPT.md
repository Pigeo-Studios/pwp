# Промпт для агента: переделка PWP (локально)

Скопируй всё ниже в агента, запущенного в `C:\Users\maska\...\PWP` (корень репо `Pigeo-Studios/pwp`).

---

Ты работаешь над PWP — тактическим шутером «Squad в Minecraft» (Forge 1.20.1-47.3.0, Java 17, Gradle 8.14, official mappings). Задача — поэтапно переписать проект грамотно, НЕ потеряв ни одной механики, модели, звука и экрана, а также переделать UI и цикл сессий (лобби → матч → лобби).

## Перед началом (обязательно)
1. Прочитай `AGENTS.md` целиком — там правила сборки, миксинов, ProGuard и список «НЕ ТРОГАТЬ».
2. Прочитай `docs/REWRITE_PLAN.md` — инвентаризация (чек-листы) и этапы. Это главный документ: отмечай `[x]` по мере переноса и дописывай детали поведения, которые находишь в старом коде.
3. Убедись, что проект собирается ДО изменений: `gradlew build -x test`. Если не собирается — сначала почини сборку, ничего другого не делай. Прод-жарники берутся из `PWPFILES_DIR` (по умолчанию `C:/Users/maska/OneDrive/Desktop/Pwpfiles`).

## Жёсткие правила
- После КАЖДОГО логического шага — `gradlew build -x test` (и `test`, когда появятся тесты). Красная сборка = не идёшь дальше.
- Один этап = отдельная git-ветка `rewrite/stage-N`, мелкие коммиты с понятными сообщениями на русском. Форматирование — ОТДЕЛЬНЫЙ коммит без логики.
- Старый код удаляется ТОЛЬКО когда новый закрыл все пункты чек-листа своей фичи в `REWRITE_PLAN.md`.
- ID ресурсов не менять (`pwpwarfare:*`, блоки, предметы, сущности, звуки, текстуры, lang-ключи) — на них завязаны построенные карты, БД китов/техники и `maps/*.json`. Модели/звуки/текстуры/анимации переносятся как есть.
- NBT-форматы `SavedData`/BlockEntity/persistentData — с миграцией (читать старый формат, писать новый), миры не должны ломаться.
- Сетевой протокол: при переходе на новый слой поднять `PROTOCOL_VERSION` (клиенты обновляются лаунчером разом). Внутри одной версии новые пакеты — только в КОНЕЦ регистрации; каждый пакет обязан быть зарегистрирован.
- Миксины: refmap + `remap=false` на чужие моды, server-only — в секцию `server` (подробно в AGENTS.md).
- ProGuard: любая рефлексия/Gson-POJO по именам полей → keep-правило в `proguard.pro`. Новый модуль → `pwpModules` в корневом `build.gradle` и `MODS_LIST` в `build.bat` (сам bat НЕ редактировать — скажи пользователю).
- Не трогать: `explosionoverhaul.mixins.json`, рабочий стол (bat-файлы, другие репо), секреты (`config.json`, `config.py`, API-ключи — не логировать и не коммитить).
- Пустые `catch` запрещены — минимум `LOG.warn(..., e)`. Никакого `System.err`. Никакого синхронного HTTP на главном потоке сервера.
- Баг чинится через причину: сначала найди причину, по возможности напиши падающий тест, потом исправь. «Страховки на страховки» не добавлять.
- Комментарии и документация — на русском. Экономь контекст: читай файлы частями, ищи grep-ом, не перечитывай то, что уже прочёл.
- В конце каждого этапа: обнови `AGENTS.md` (удали устаревшее, история инцидентов — только как короткое правило) и отчитайся: что сделано, что проверить руками в игре (список сценариев).

## Порядок этапов
Следуй этапам 1–7 из `docs/REWRITE_PLAN.md`. Приоритетные блоки ниже встраиваются так: **Цикл сессий** — сразу после этапа 2, **UI** — этап 6, но UI-кит (6.1) делается в конце этапа 2, чтобы новые экраны этапов 3–5 сразу писались на нём.

### Этап 1 — дополнительно (дыры, найдены при аудите)
- `PacketAction` / `PacketApiAction` (`equipCosmetic`): сервер вызывает `CoreServerApi.grantItem` по `skinId` от клиента — любой может выдать себе любой скин. Экипировать только то, чем игрок владеет (проверка на core-service). Убрать `Thread.sleep(200)`.
- Права saveSkin/deleteSkin/deleteFactionVehicle и редакторов — через permission level / роль, не `isCreative()`.
- `CoreServerApi` static-блок: глобальный trust-all SSL для всей JVM — убрать.
- `pwp-core-client` не должен зависеть от `pwp-core-server` — общий код в новый `pwp-api`; удалить `CoreAPI` (дубль).
- URL-параметры экранировать (`getLeaderboard` orderBy и т.п.).

### Блок «Цикл сессий» (лобби → матч → лобби)
Сейчас логика размазана: `pwp-lobby` (`ServerManager` — `ProcessBuilder` + `cmd.exe robocopy match_template`, `MatchAllocator`, `VotingManager`, `LobbyMod` 779 строк), `pwp-warfare` (`GameLogicEvents.returnToLobbyTimer` — статик-таймер, `MatchStatsTracker.scheduleServerShutdown(180)` → `server.halt`, `MatchHeartbeatSender`), `TransferHosts` (pwp-core-server), бот-шедулер (`bots/scheduler_loop.py`, `pwp-scheduler/`).
1. Сначала составь в `REWRITE_PLAN.md` раздел «Цикл сессий: как сейчас» — диаграмма состояний и все места, где состояние меняется; список известных/найденных багов (зависшие матчи, игроки не возвращаются, повторный заход, порт занят, мусорные `match_*`, двойной старт голосования, гонки при переносе).
2. Сделай явную машину состояний с одним владельцем: `LOBBY_IDLE → VOTING → ALLOCATING → STARTING → PLAYING → ENDING → RETURNING → SHUTDOWN` (матч) и пул матч-серверов в лобби. Каждый переход — одна функция, логируется, с таймаутом и откатом (не поднялся за N сек → откат, порт освобождён, игрокам сообщение).
3. Переносы игроков идемпотентные (повтор не ломает), с повторной попыткой и fallback «вернуть в лобби». Выход/вылет игрока в любой фазе обрабатывается.
4. Завершение матча: сохранить статистику (асинхронно, с ретраем) → вернуть игроков → дождаться, что все ушли или таймаут → корректный `server.halt` → лобби помечает слот свободным по heartbeat-таймауту, удаляет `match_*` директорию.
5. Восстановление после краха: лобби при старте находит осиротевшие `match_*`/процессы/порты и прибирает; heartbeat пропал → матч считается мёртвым.
6. Источник правды о матчах — один (core-service `Match` API или лобби — выбери, задокументируй), остальные только читают.
7. Тесты на машину состояний (чистая логика без Forge) — все переходы, таймауты, повторы.

### Блок «UI» (этап 6 + UI-кит раньше)
- 6.1 UI-кит в `pwp-core-client` на `PWPTheme`: Panel, Button, IconButton, Tabs, ScrollList, Tooltip, RadialMenu, ContextMenu, Modal, ProgressBar, Toast. Только `GuiGraphics`, все цвета/отступы/шрифты из `PWPTheme` (сейчас ~175 захардкоженных `0xFF...` в warfare/client — должно стать 0). Анимации (фейд/слайд/hover) — общий `UIAnim` с easing, время от `partialTick`/реального времени, не от тиков.
- Референс стиля: `.opencode/plans/PWP-DESIGN-REFERENCE.md`. Ориентир по UX — Squad (деплой, карта, радиалки, командирский интерфейс).
- Контекстные окна как в Squad: ОДНО радиальное/контекстное меню + провайдеры действий по объекту (хаб, ящик, техника, игрок, постройка, точка на карте) — заменяет 8 отдельных радиалок.
- Перевести экраны: лобби (MainMenu/Lobby/Selection/Loading/Stats, вкладки Play/Leader/Vote), DeployScreen, SquadMapScreen, выбор команды/фракции/кита, VictoryScreen, DownedScreen, редакторы, HUD (`WarfareOverlay` → независимые элементы).
- Каждый экран — состояние приходит с сервера DTO (как `LobbyStatePacket`), клиент не вычисляет игровую логику.
- Адаптив: всё считается от `width/height` экрана и GUI scale, проверить на 1280×720 и 1920×1080 при GUI scale 2–4.

## Чего не хватает (делать в своих этапах, не раньше)
Полный набор построек как в Squad (через `StructureDef` + `BuildService`), материалы и патроны как ресурсы хаба/ящика/грузовика, хабы/FOB-радиус и постройки на карте, нормальная карта (генерация текстуры из мира, сетка Squad), единая система меток, рендер персонажа, анимации. Если требование неясно (например «не хватает двух типов») — спроси пользователя, не выдумывай.

2. Что удалено из старого кода.
3. Что проверить в игре руками — конкретные сценарии.
4. Риски/что осталось.
