- **СБОРКА ЛАУНЧЕРА (PWP-Launcher) — ТОЛЬКО `npm run tauri build`** (инкрементально быстро, `--no-bundle` если нужен только exe). Голый `cargo build --release` ЗАПРЕЩЁН: без env-переменных tauri CLI бинарь собирается в dev-режиме — интерфейс НЕ встраивается, окно грузит `http://localhost:1420` (devUrl) → у всех пользователей «Не удается открыть эту страницу, localhost отказано в подключении» (инцидент 06.08.2026, v4.1.12). Симптом в exe: нет строк `index-*.js`/`index-*.css` (ассеты фронта), есть `1420`. После `npm run tauri build` проверять, что ассеты встроены (размер exe ~5.7МБ, в бинарнике присутствует `index-<hash>.js`). Релиз-файл — сырой `src-tauri\target\release\pwp-launcher.exe`, переименованный в `PWPLauncher_v<ver>_portable.exe` + GitHub release + подпись `launcher-version.json` через `scripts/sign-file.mjs`
- **СЕССИЯ ЛАУНЧЕРА НЕ УМИРАЕТ ПРИ ОБРЫВАХ СВЯЗИ (архитектура v4.1.18, с 11.08.2026)**: главное правило — сессия (state.json + токены) стирается ТОЛЬКО когда сервер определённо сказал «нет» (refresh/heartbeat success:false после всех попыток, 401+401, локальный экспайр refresh 30 дней). Сеть/часы/БД-сбой → сессия сохраняется, статус «Нет связи». Инцидент 11.08.2026: релиз v4.1.17 НЕ содержал фикс обрыва сети во время refresh (коммит был, но не доехал до релиза) — «выбивает по кд» ровно каждые 30 мин (жизнь access-токена) при отвалившемся сервере. Механика: `restore_session` — restore-first (сессия отдаётся СРАЗУ из state.json, валидация — в фоне в App.tsx: сразу после restore + каждые 5 мин + при запуске игры; раньше гонял validate_session до 30с ретраев и пользователь видел окно входа); `refresh_once(force)` — force=true делает РЕАЛЬНЫЙ обмен токенов даже если access локально валиден (нужен в 401-ветке и при heartbeat success:false — иначе повтор с тем же токеном = вечный 401); heartbeat success:false → принудительный refresh + повторный heartbeat, чистка только после ДВУХ отказов подряд; REFRESH_LOCK (TokioMutex) против параллельных refresh. **КОНВЕНЦИЯ 503**: сервер отвечает HTTP 503 (НЕ success:false и НЕ 401) на все транзиентные ошибки БД — `AuthMiddleware.findSessionSecret` (SQLException пробрасывается → 503 вместо «no valid session»), `AuthController.heartbeat`/`refresh` (SQLException → 503). Лаунчер классифицирует 503 как Network → сессия сохраняется. success:false — только когда сессия реально не найдена/истёк токен. **ACCESS-ТОКЕН НЕ РОТИРУЕТСЯ ПРИ REFRESH (фикс 11.08.2026)**: `AuthController.refresh` ротирует ТОЛЬКО refresh_token/session_key/hmac_secret, access-токен остаётся прежним (`currentAccess`). Причина: access-токен держит запущенный игровой клиент до конца сессии (передаётся в `--accessToken`, используется в `/session/minecraft/join` при входе на любой сервер); ротация access в разгар игры инвалидировала токен клиента в БД → его joinServer молча получал 403 → «lost connection: Disconnected» при возврате в лобби (инцидент 11.08.2026, 17:56:48 — refresh лаунчера 17:50:47 ротировал токен). `AuthLibController.handleJoin` при invalid/rotated токене МОЛЧАЛИВО 403 без лога — теперь пишет `JOIN FAIL` warn (serverId/profile) для видимости в core-service.log. Ротация access допустима ТОЛЬКО при создании новой сессии (login/confirm-2FA) — клиент только стартует и получает свежий токен
